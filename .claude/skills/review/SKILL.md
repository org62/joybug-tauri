# Joint review and fix

1. **Choose and preserve scope.** State scope before editing. Explicit `/review` without a scope means staged changes in **both** the parent and `external/joybug-core`, even if the parent gitlink is not staged. Automatic post-major-change use means the current task's uncommitted changes: tracked `git diff HEAD` plus relevant untracked task files in both repositories. Never silently switch modes. In each repository gather `git status --short`, `git diff --cached --name-status`, `git diff --cached`, and `git diff`; inspect new files in scope. Preserve a read-only baseline of scope, `git ls-files --stage`, and existing unstaged edits. An empty index in one repository means its unchanged code is contract context; if both indexes are empty in staged mode, report no staged code and stop.
   - If the parent stages a changed core gitlink, also review the core commit range from the parent's HEAD gitlink to its indexed gitlink; deduplicate overlaps with core's staged patch. Missing submodule or referenced commits means incomplete coverage, never a clean verdict.
   - For partially staged files, review indexed content (`git show :<path>` in its owning repository), then inspect worktree content to apply fixes safely. Preserve user edits. **Never stage, commit, reset, stash, checkout, or alter the gitlink.** Tests exercise the final worktree, not necessarily the original staged patch; distinguish them in the result.
2. **Map contracts before judging.** Read relevant full functions, equivalents, callers, tests and docs beyond hunks. Trace core bookkeeping/platform/protocol → Tauri commands/session/events → React hooks/context/views, plus affected scripting consumers. Use language-server references where available before exported changes; otherwise scoped searches with inspected consumers. Before deleting a symbol, prove it has no meaningful users, including registration, serialization, Lua exposure and conditional platform paths.
   - For substantial patches, map boundaries first, then assign independent read-only review slices (core semantics/performance; UI/Tauri lifecycle/presentation; shared contracts/duplication/docs when substantial). Supply the same cross-repo contract and named scope. Integrate evidence centrally, resolve contradictory recommendations against code, and apply fixes with one owner; no overlapping edits or isolated sign-offs. Small patches use the same checks inline. Parallel reviews never replace tracing a request across boundaries.
3. **Check the changed paths and their consequences.** Search for existing implementations in both repositories before retaining another.
   - **Correctness and sound design:** invariants, races/stale replies, lifecycle/error paths, platform/architecture semantics, hidden contract changes. Correct the owning cause, not swallowed exceptions, magic delays, special cases, fake fallbacks or a second source of truth.
   - **Dead code and leftovers:** obsolete branches, helpers, imports, registrations, aliases, schemas/callers, tests/comments, temporary diagnostics and newly unnecessary dependencies. Complete the cutover.
   - **Duplication and responsibilities:** consolidate genuinely identical behavior under its existing owner and migrate every caller. Core owns debugger/platform semantics; Tauri owns orchestration/serialization; React owns presentation/interaction. Keep intentionally different platform semantics distinct. Do not build a framework to shorten similar-looking code.
   - **Maintainability and readability:** explicit invariants, coherent names, direct control flow, understandable ownership/lifetimes and narrow interfaces another engineer can change in six months. Prefer existing conventions and plain functions; no personal-style churn or speculative abstractions.
   - **Performance:** frequency and total work, paused-session serialization, lock duration, per-thread/per-row work, native queries, allocations/copies, repeated decoding/symbolization, IPC fan-out, refresh/polling and rerenders. Remove demonstrated avoidable work while preserving semantics. Ground costs in counts, complexity, measurements or a targeted runtime comparison; never call an unmeasured change faster. No caches, retries, telemetry or frameworks without concrete need.
   - **Documentation:** compare affected behavior/APIs/commands/platform limits with docs and examples in both repositories. Correct the authoritative section and incorrect examples; trim stale, redundant or misleading text in scope. Explain non-obvious contracts, not each implementation line; link rather than duplicate. Do not create review reports or documentation files merely to narrate changes.
   - **Verification quality:** consumer behavior, errors, boundaries and transitions. Delete obsolete implementation/wording assertions rather than repinning them. Regression coverage must catch concrete bugs or uncertain edges, not mock echoes or copied implementation.
4. **Fix only evidenced issues.** For each fix identify exact location, observable failure or concrete maintenance/performance cost, and root-cause correction. Fix confirmed issues in both repositories without routine permission and without staging; reuse utilities and update all affected callers/tests/docs, with no internal compatibility shims. Keep speculation separate; no finding quota. If established contracts cannot determine a user-visible semantic choice, ask only about that choice and continue independent work. Preserve conflicting unstaged user work and ask about the specific conflict rather than overwriting it.
5. **Verify integrated fixes.** Reproduce behavioral defects before fixing when practical. Read the existing `e2e` and `ui-smoke` skills for setup rather than duplicating recipes. After integration run affected core tests and the required E2E suite, and exercise changed UI/CLI behavior for runtime proof. Add focused behavior regressions only for real bugs or uncertain edges. Treat flakes as defects; fix their cause and use the existing repeat harness, never retries to hide failures. Separate executed proof, static conclusions, skipped tests and unavailable-platform checks. Confirm original index entries in both repositories (including gitlink) remain unchanged.
6. **Report briefly and calibrate.** Findings/fixes: severity, repository/path/symbol, impact, correction; then commands/scenarios actually exercised, platform/evidence gaps and remaining blockers. If no confirmed findings, say so with scope, not a promise of bug absence. Keep code/doc fixes separate from skill refinements. Refine this skill only for an observed instruction failure (scope misses, duplicate advice, weak evidence, ownership conflicts, needless abstractions or excess reporting); repeat the affected step on the same patch and describe the improvement. No observed failure means leave it intact.
